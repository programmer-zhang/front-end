# 区块链安全(七): 零转账诈骗

> 本文使用 Grok 辅助编写

## 阅读本文您将收获
* 零转账诈骗和地址投毒的本质区别
* `transferFrom(from, to, 0)` 为什么不需要受害者签名
* 三种投毒手法怎么在浏览器里对上号
* 真实案例怎么核对「目标地址」和「钓鱼地址」
* 用户侧 / 钱包侧的可执行防御清单

## 先把概念拆开

零转账诈骗（Zero Transfer Phishing）不是单独一类「新协议漏洞」，它是 **地址投毒（Address Poisoning）** 里杀伤力最大的一种投毒方式。

三件事必须分开看：

| 名称 | 攻击者做了什么 | 受害者看到什么 | 钱是怎么丢的 |
|---|---|---|---|
| 假充值（系列一） | 用假合约发 `Transfer` 事件 | 「我收到了一笔 USDT」 | 先发货 / 先放币 |
| 授权诈骗（系列二） | 骗你签 `approve` / `permit` | 「这是一次普通授权」 | 攻击者后续 `transferFrom` 把币转走 |
| 零转账 / 地址投毒 | 往你的历史记录里塞一个长得很像的地址 | 「这个地址我转过 / 收过」 | **你自己**把真币转到钓鱼地址 |

关键差异：

* 不偷私钥
* 不需要你签名授权
* 链上交易是成功的、合法的
* 损失发生在你下一次「复制历史地址再转账」的时候

所以浏览器里这笔 0 USDT 看起来「没问题」，正是攻击成功的前提。

## 攻击为什么成立

人眼扫 40 位十六进制地址，默认只看头尾。攻击者就利用这一点。

假设你刚给交易所热钱包转过一笔 USDT：

```
真实目标: 0xa7B4BAC8f0f9692e56750aEFB5f6cB5516E90570
钓鱼地址: 0xa7Bf48749D2E4aA29e3209879956b9bAa9E90570
```

头 4 位 `0xa7B`、尾 6 位 `E90570` 一样，中间全换。钱包历史列表通常只展示缩写：

```
0xa7B4...E90570
0xa7Bf...E90570
```

这两行在手机屏幕上几乎不可区分。

接下来只差一步：让钓鱼地址出现在你的「转账记录」里。零转账就是完成这一步的最低成本方法。

## 三种投毒方式

地址投毒分成三类，链上表现不一样，识别点也不一样。

### 1. 尘埃转账（Dust Transfer）

攻击者控制一个「长得像你常用收款方」的地址，从该地址给你转 `0.000001 USDT` 这类尘埃级金额。

* 用的是 **官方代币合约**
* `from` = 钓鱼地址，`to` = 你
* `value` 极小但大于 0
* 你的余额会真的增加一丁点

识别：不明来源的极小额入账，且对手地址和你最近用过的地址头尾相似。

### 2. 零值转账（Zero-value Transfer）——本文重点

攻击者不从钓鱼地址给你打币，而是调用官方代币合约：

```solidity
token.transferFrom(victim, lookalike, 0);
```

效果是：浏览器 / 钱包的 Token Transfer 列表里多出一条

```
from:  你的地址
to:    钓鱼地址
value: 0 USDT
token: 官方 USDT / USDC
```

看起来像 **你曾经给这个地址转过账**。这比「别人给我转了 0 U」更危险，因为用户复制地址时更倾向选「我转过的收款方」。

### 3. 假代币镜像转账（Counterfeit Token）

攻击者自己发一个名叫 `USDT` / `USDC` 的假合约，强制 `emit Transfer(victim, lookalike, 20000000e6)`。

* 合约地址不是官方地址
* 金额可以做成和你上一笔真转账一模一样
* 有些钱包只按 `symbol` 展示，不展示合约

这一类和系列一「假充值」同源，但目的不同：假充值骗「已到账」，这里骗「这个地址我用过」。

## 技术拆解：0 为什么能转成功

以常见的 ERC-20 实现为例：

```solidity
function transferFrom(address from, address to, uint256 value) public returns (bool) {
    uint256 allowed = allowance[from][msg.sender];
    require(balanceOf[from] >= value);
    require(allowed >= value);          // 关键
    balanceOf[from] -= value;
    balanceOf[to]   += value;
    if (allowed != type(uint256).max) {
        allowance[from][msg.sender] = allowed - value;
    }
    emit Transfer(from, to, value);
    return true;
}
```

攻击者从未获得过你的 `approve`，所以：

```
allowance[victim][attacker] == 0
```

不等式变成：

```
require(0 >= value);
```

唯一能过的取值是 `value == 0`。

余额检查同样成立：`balanceOf[victim] >= 0` 恒真。加减都是 0，状态不变，但 **`Transfer` 事件照样发出**。

钱包和浏览器索引的是事件，不是「是否发生了价值转移」。于是你的历史里出现一条「你 → 钓鱼地址，0 USDT」的成功记录。

整笔交易的 `tx.from` 是攻击者自己的 EOA 或投毒合约，**不是你**。这是链上判定「这是投毒而不是你主动转账」的最硬字段。

对照关系：

```
交易发送者 tx.from     = 攻击者 / 投毒合约     ← 谁付的 gas
事件 from              = 受害者地址           ← 被写进历史的「付款人」
事件 to                = 钓鱼相似地址         ← 准备让你下次复制的地址
事件 value             = 0
token 合约             = 官方 USDT / USDC
```

USDT（Tether ERC-20）的实现细节和标准 OpenZeppelin 不完全一样，但 `value == 0` 时同样不要求有效授权，攻击路径成立。TRC-20 / BEP-20 上官方稳定币也长期能被同样方式刷事件。

## 完整攻击链路

```
1. 监听
   扫链监控大额 USDT / USDC transfer
   取出 (victim, realRecipient, amount)

2. 撞地址
   离线或用 vanity 工具生成
   与 realRecipient 前 4~6 位、后 4~6 位相同的地址
   转入一点点 gas / 稳定币备用

3. 投毒
   方案 A: lookalike --(0.000001 USDT)--> victim
   方案 B: transferFrom(victim, lookalike, 0)     ← 零转账
   方案 C: 假 USDT 合约 emit 同等金额的 Transfer

4. 等待
   你下一次从「最近转账」里复制地址
   或先小额试转，再大额跟进
   ——试转如果复制的已经是钓鱼地址，等于帮攻击者做确认

5. 收割
   你主动把真 U 转到 lookalike
   攻击者立刻拆分、跨链、进交易所
```

攻击成本：一次 `transferFrom(..., 0)` 的 gas。收益：整笔被复制走的转账。不需要和你聊天，不需要你点链接。

## 链上怎么一眼看出来

打开 Etherscan / BscScan / Tronscan 的 Token Transfers，按下面清单核对。

### 判定零转账投毒

1. `value == 0`，代币却是官方 USDT / USDC
2. 事件 `from` 是你，但交易发起人 `tx.from` 不是你
3. 事件 `to` 和你最近一笔真实收款地址头尾相似、中间不同
4. 同一区块或前后几分钟，对多个大额地址批量出现同类 0 转

### 判定尘埃投毒

1. 入账金额是 `10^-6` ~ `10^-3` 量级
2. 发送方地址和你常用收款方头尾相似
3. 该发送方除了给你打灰尘，没有正常业务往来

### 判定假币镜像

1. `symbol` 是 USDT / USDC，合约地址对不上官方
2. 金额、精度刻意做成和上一笔真转账相同
3. 代币没有正常流动性，或浏览器已标 `Phish / Fake`

官方合约必须硬核对，不要看名字和图标：

| 链 | 代币 | 官方合约 |
|---|---|---|
| Ethereum | USDT | `0xdAC17F958D2ee523a2206206994597C13D831ec7` |
| Ethereum | USDC | `0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48` |
| TRON | USDT | `TR7NHqjeKQxGTi8q8ZY4pL8otSzgjLj6t` |

## 真实案例

以下地址来自公开链上安全事件，只用于对照头尾相似，不要向这些地址转账。

### 案例 1：2023 年 2000 万 USDT

PeckShield / Cointelegraph 披露。

```
受害者准备转到:
0xa7B4BAC8f0f9692e56750aEFB5f6cB5516E90570

实际转到钓鱼地址:
0xa7Bf48749D2E4aA29e3209879956b9bAa9E90570
```

对比：

```
真:  0xa7B4 BAC8 f0f9 692e 5675 0aEF B5f6 cB55 16E9 0570
假:  0xa7Bf 4874 9D2E 4aA2 9e32 0987 9956 b9bA a9E9 0570
        ^^^^                                    ^^^^^^
```

攻击者先对受害者地址做了 0 USDT 转账投毒。受害者从历史记录复制地址，把刚从币安提出的大额 USDT 转了出去。Tether 随后冻结了钓鱼地址。

### 案例 2：2025-05-26 同一人中招两次，约 260 万 USDT

TenArmor / Cyvers 披露。

```
受害者:
0x86C0300Fc369E54d22512564Cc0e8CC261102604

本意收款方:
0x4668d1fe87444a4d7508e83c89bfdaf1117e6b76

钓鱼地址:
0x4668EE748c88DA4FEc595773b22f96f366eD6B76
```

对比：

```
真:  0x4668 d1fe ... 117e 6b76
假:  0x4668 EE74 ... 366e D6B76
        ^^^^              ^^^^
```

三小时内连续两笔（约 84.3 万 + 175 万 USDT）都进了同一个钓鱼地址。说明投毒记录一旦留在历史里，会反复生效。

### 案例 3：2025 Q4 SlowMist 通报，试转之后大额跟错

SlowMist 2025 Q4 MistTrack 报告：用户先向正确地址小额试转，几分钟后把约 5000 万美元打到头尾相似地址。

```
用户地址:
0xcB80784ef74C98A89b6Ab8D96ebE890859600819

正确目标:
0xbaf4b1aF7E3B560d937DA0458514552B6495F8b5

钓鱼地址:
0xBaFF2F13638C04B10F8119760B2D2aE86b08f8b5
```

试转不能防这类攻击。试转如果复制的是历史里的投毒地址，只是给攻击者多一笔确认。

## 和系列里其他手法的边界

* **vs 假充值**：假充值骗收款方「U 已经到了」；零转账骗付款方「这个地址我用过」。前者看合约地址，后者看历史里的对手地址是谁写进去的。
* **vs 授权 / Permit / 7702 / Drainer**：那些要你签名。零转账在投毒阶段 **完全不需要你签名**，你的第一次主动签名就是把真钱转出去。
* **vs 系列十一提到的地址污染**：十一把它列为钓鱼手法之一。本文补的是它能写进历史的合约原因：`value == 0` 绕过了 `allowance` 检查。

## 防范

### 用户侧（按优先级）

1. **禁止从交易历史复制地址**。地址只从地址簿、官方站点或硬件钱包屏幕取。
2. 粘贴后核 **完整 42 位**，不要只看头尾。习惯对中间 4~8 位。
3. 看到 `0 USDT` / `0 USDC` 入账或「自己转出 0 U」——默认当投毒，不要点开后再复制对手地址。
4. 小额试转必须使用 **同一条刚核对过的完整地址**，不要回历史记录重新复制。
5. 大额转账走硬件钱包，屏幕上的目的地址再对一次。
6. 钱包能隐藏 0 值转账、未知代币、垃圾空投的，全部打开。

### 开发者 / 钱包侧

1. Token 列表默认过滤 `value == 0`。
2. 若 `tx.from != event.from` 且 `value == 0`，打上「非主动转账 / 可能是地址投毒」。
3. 历史展示不要只显示 `0x1234...abcd`，中间位也要给核对方。
4. 相似地址检测：和用户常用收款方头尾相同、中间不同的，直接标红。
5. 充值、提现、OTC 后台不要只解析 `Transfer` 事件，必须校验：
   * 合约地址 == 官方
   * `value > 0`
   * 实际 `balanceOf` 增加
   * `tx.from` 与业务语义一致

### 平台侧（交易所 / 收款方）

大额入账除了确认数，再对一次「发送方是否为用户事先登记的地址」。被投毒的是付款人，但收款平台用白名单能挡住一部分「转错之后无法追回」的客诉。

## 排查模板

发现自己历史里多了 0 U 记录时，按这张表填一遍：

```
交易哈希:
链:
代币合约:            （是否官方？）
tx.from:             （是不是你？不是 → 投毒）
event.from:
event.to:
value:
event.to 和常用收款地址:
  前 4 位是否相同:
  后 4 位是否相同:
  中间是否不同:
结论: 投毒 / 正常
处理: 忽略该条，地址簿重新粘贴正确地址
```

## 总结

零转账诈骗的攻击面不在签名，在 **ERC-20 允许 `transferFrom(..., 0)` 并照样发事件**，加上钱包用缩写展示长地址。

判定就三句话：

1. `value` 是 0，但出现在你的 Token 历史里
2. 付出 gas 的人不是你
3. 对手地址和你真正要转的地址头尾一样、中间不一样

防御也是三句话：地址簿、全量核对、把 0 值转账从 界面 里隐藏掉。
