# IEEE 754 的四种舍入方向

### 写在前面
> 在[《JS 浮点数计算》](./js浮点数计算.md)一文中，浮点数运算的六个步骤里提到了「舍入处理」，但只简单介绍了默认的就近舍入。实际上，`IEEE 754` 标准定义了 **四种舍入方向（rounding direction）**，它们不仅在浮点数存储时起作用，还悄悄决定了 JS 中 `Math.round`、`Math.floor`、`Math.ceil`、`Math.trunc` 这些方法的行为差异。本文把这四种舍入方向彻底讲清楚。

## 阅读本文您将收获
* `IEEE 754` 四种舍入方向的准确定义与区别
* 「银行家舍入」与普通四舍五入的区别
* 四种舍入方向在 JS 中的对应实现
* `0.1 + 0.2 !== 0.3` 中舍入的完整推演

## 为什么需要舍入

> 浮点数的精度是有限的：双精度浮点数的尾数只有 52 位（加上隐含位共 53 位有效数字）。

* 大多数十进制小数转换成二进制后是**无限循环小数**（如 `0.1`）。
* 浮点数运算（对阶、尾数计算、规格化）过程中，尾数右移会**移出低位**。
* 无论哪种情况，最终结果都无法被 64 位完整容纳，必须丢弃多余的位——**丢弃的策略就是舍入方向**。

> 一次舍入最多产生 `0.5 ulp`（unit in the last place，末位单位）的误差，标准通过规定舍入方向来控制误差的传播。

## 四种舍入方向总览

| 舍入方向 | 英文名 | 规则 | 误差特性 |
| --- | --- | --- | --- |
| 就近舍入，平局取偶 | Round to nearest, ties to even | 舍入到最近的可表示数；两边一样近时取尾数为偶数的一方 | 单次误差 ≤ 0.5 ulp，**累计误差最小** |
| 向 +∞ 舍入 | Round toward +∞ | 向正无穷方向取最近的可表示数（结果只会 ≥ 真实值） | 结果偏大或相等 |
| 向 -∞ 舍入 | Round toward -∞ | 向负无穷方向取最近的可表示数（结果只会 ≤ 真实值） | 结果偏小或相等 |
| 向零舍入 | Round toward zero | 向零方向取最近的可表示数（直接截断） | 结果绝对值偏小或相等 |

```
以数轴直观理解（真实值落在两个可表示数 a < x < b 之间）：

        a          x          b
 向-∞ ──────►     ▼    ◄────── 向+∞
        ◄──────────┼──────────► 向零（x>0 时向左，x<0 时向右）
                   │
        谁近取谁；一样近取尾数为偶数的那个（就近舍入）
```

> `IEEE 754` 标准要求所有实现**必须**支持「就近舍入，平局取偶」，其余三种方向是可选的（但几乎所有主流硬件都支持）。四种方向构成了四个"舍入模式"，运算时可以切换。

## 1. 就近舍入，平局取偶（默认模式）

### 规则
* 找到离真实值最近的两个可表示数，取**更近**的那个。
* 如果两边距离**完全相等**（平局，tie），取**尾数末位是 0（即偶数）** 的那个。

### 和四舍五入的区别
普通四舍五入是 "ties away from zero"（平局远离零），而 IEEE 754 默认模式是 "ties to even"（平局取偶）：

```
普通四舍五入（ties away）：
  1.5 -> 2      2.5 -> 3      3.5 -> 4      0.5 -> 1     -1.5 -> -2

就近舍入，平局取偶（IEEE 754 默认）：
  1.5 -> 2      2.5 -> 2      3.5 -> 4      0.5 -> 0     -1.5 -> -2
              (2.5 取偶数 2)              (0.5 取偶数 0)
```

### 为什么要"取偶"而不是普通的"逢五进一"？
* 逢五进一会让平局**永远向上偏**：大量数据累加时误差单调增长（比如财务计算，+0.5 +0.5 +0.5... 永远偏大）。
* 取偶让平局"一半向上、一半向下"（上一局进位后变偶数，下一局就舍去），**长期累计误差趋近于零**，统计学上更公平。因此它也被称为**银行家舍入（Banker's Rounding）**。

### 二进制视角的例子
> 假设某个 4 位尾数的场景（实际是 53 位，此处简化），可表示数尾数间隔为 `0.001`（二进制）：

```
真实值 1.0110（二进制尾数），恰好落在 1.01 和 1.10 正中间 —— 平局！
  1.01 尾数末位是 1（奇数）
  1.10 尾数末位是 0（偶数）  ← 取这个

真实值 1.0111，离 1.10 更近 —— 非平局，直接取 1.10
```

### JS 中的体现
* **浮点数存储和运算**使用此模式，这就是 `0.1 + 0.2 !== 0.3` 推演中最后一步的舍入方式。
* ⚠️ 注意：`Math.round` **不是** IEEE 754 默认模式——它对 `.5` 是"向上取整"（`Math.round(2.5) === 3`、`Math.round(-2.5) === -2`，即 ties toward +∞），且 `Math.round(-0.5) === -0`。
* `toFixed` 的舍入依赖浮点数的**实际二进制值**，不是十进制四舍五入：`1.005.toFixed(2)` 结果是 `"1.00"`，因为 `1.005` 实际存储的是 `1.00499999999999989...`。

## 2. 向 +∞ 舍入

### 规则
* 取**大于等于**真实值的最近可表示数，宁可放大，绝不缩小。
* 对正数：尾数进位；对负数：直接截断（丢弃的位使绝对值变小，即数值变大）。

```
  1.23 -> 1.24 (若 1.23 不可表示)     -1.23 -> -1.23（截断即可，-1.23 > -1.24）
```

### JS 中的对应
* `Math.ceil` 的语义与它一致（对普通数而言）：

```js
Math.ceil(1.2);   // 2
Math.ceil(-1.2);  // -1  （-1 > -1.2，向 +∞）
Math.ceil(0.1 + 0.2 === 0.3 ? 0 : 0.30000000000000004); // 1
```

### 应用场景
* 计算"至少需要多少"：分页总页数 `Math.ceil(total / pageSize)`、内存对齐分配、缓存容量预估——保证不低估资源需求。

## 3. 向 -∞ 舍入

### 规则
* 取**小于等于**真实值的最近可表示数，宁可缩小，绝不放大。
* 对正数：直接截断；对负数：尾数进位（绝对值变大，数值变小）。

### JS 中的对应
* `Math.floor` 的语义与它一致（对普通数而言）：

```js
Math.floor(1.8);    // 1
Math.floor(-1.2);   // -2  （-2 < -1.2，向 -∞）
```

### 应用场景
* 计算"最多可以用多少"：可整除的块数、时间戳取整天（`Math.floor(ts / 86400000)`）。
* ⚠️ 与 `parseInt` 截断负数的行为不同：`Math.floor(-1.5) === -2`，而 `parseInt('-1.5') === -1`——后者其实是向零舍入。

## 4. 向零舍入

### 规则
* 取**绝对值更小**（更靠近 0）的最近可表示数，等价于**丢弃尾数多出的低位**，即"截断（truncation）"。
* 正数表现为向下，负数表现为向上——方向始终指向 0。

### JS 中的对应
* `Math.trunc`（ES6）与它语义一致；更早的惯用写法是 `x | 0`、`x >> 0`、`x >>> 0`（受 32 位限制，见《JS 中的按位运算》）：

```js
Math.trunc(1.8);   // 1
Math.trunc(-1.8);  // -1
1.8 | 0;           // 1
-1.8 | 0;          // -1
```

### 应用场景
* 只要整数部分、不关心方向的场景：金额取整展示、下标计算、Hash 计算。
* 它也是 `ToInt32` / `ToUint32` 抽象操作（位运算的前置转换）使用的舍入方式。

## 回看 0.1 + 0.2 的舍入

> 母文章运算详情第 5 步，正是「就近舍入，平局取偶」的一次实战：

```
精确和： 1.01100110011...0011（超出 52 位） * 2^-2
   尾数需保留 52 位，多出两位：...011 **0 1**
                                        │ └─ 超出位（非零，说明不是精确平局）
                                        └─── 保留位

舍入判断：超出部分大于"一半 ulp"，向就近方向进位
   ...0011 + 1 => ...0100（尾数末位进位）

得到： 0.3000000000000000444089209850062616169452667236328125
     十进制展示为 0.30000000000000004
```

* 如果当时采用的是「向零舍入」，多余位会被直接截掉，`0.1 + 0.2` 反而会**恰好等于 0.3**。
* 如果采用「向 ±∞」，结果会更大或更小。
* 可见**同一个运算，舍入方向不同，结论完全不同**——这就是标准把默认方向固定为"就近舍入，平局取偶"的原因：它让单次误差最小且无系统性偏差。

## 四种方向在 JS 中的速查

```js
const x = 2.5;

// 就近舍入，平局取偶：JS 没有直接暴露，浮点运算内部自动使用
// 向 +∞
Math.ceil(x);                       // 3
// 向 -∞
Math.floor(x);                      // 2
// 向零
Math.trunc(x);                      // 2
x | 0;                              // 2（32 位整数范围内）

// 注意 Math.round 的 "平局向上" 不是 IEEE 754 的任何一种方向
// （-0.5 向上得 -0，+0.5 向上得 1，本质是 floor(x + 0.5) 的语义）
Math.round(x);                      // 3
```

## 解决方式
1. 对精度敏感的场景（金额计算），先乘以倍率转成整数运算，规避舍入误差。
2. 比较浮点数时用**误差范围**代替全等：`Math.abs(a - b) < Number.EPSILON`。
3. 需要精确十进制行为时引用类库 [decimal.js](http://mikemcl.github.io/decimal.js/) / [Math.js](https://mathjs.org/)，它们在软件层自定义了舍入方向。
4. 理解 `Math.round / floor / ceil / trunc` 与四种舍入方向的映射关系，根据业务语义选择正确的方法，而不是无脑 `parseInt`。
